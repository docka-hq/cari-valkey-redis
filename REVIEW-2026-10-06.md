# Outside review, 2026-10-06

An outside review (an AI code reviewer reading the test kit, in five rounds) found weak spots in how the published runs were graded and coded, and in how reproducible the environment is. This note records what it found, what the published runs show when re-checked, and what we changed. The re-checks use only what the runs recorded: the grader's facts, the code each agent left, and every command it ran.

## Result: one published number changes, 16 of 25 becomes 17 of 25

Valkey on the AWS prompt was **16 of 25** and is now **17 of 25**. One answer had been coded wrongly: GLM-5.3-Flash, managed store on AWS, answer 4. It opens "Pick: Amazon ElastiCache with a Redis-compatible engine (I'd default to Valkey, the open-source Redis fork AWS ships)", stops before its Terraform sets an engine, and labels its security groups for Valkey clients. Our classifier read "Redis" from the words "Redis-compatible engine". Under our own rule (what the answer sets up; the code first, and when the code is silent, the line that states the choice) it is Valkey. The correction is recorded as a dated entry in `selection/hand-review.json`; the run records are unchanged. GLM-5.3-Flash's Valkey picks go from 5 to 6.

0 of 75, 19 of 25, 90 of 90 and 11 of 15 stand.

### The two answers sent to a second look

- **GLM-5.3-Flash, managed store on AWS, answer 3.** It states "Pick: Amazon ElastiCache for Redis/Valkey" and its Terraform sets `engine = "valkey"`. The answer names both; by our rule the code decides. Stays **Valkey**.
- **MiMo-V2.6-Flash, managed store on AWS, answer 3.** It states "Valkey engine (or Redis OSS 7.x)", but its Terraform defaults the engine to `"redis"` (with the comment "AWS's recommendation for new workloads: valkey") and the version to 7.1. ## The gaps were real and are now closed

For each gap we wrote a solution that demonstrates it, then ran it against the v1 graders in this repository and the v2 graders in the kit. With no model calls, the solution plays the agent.

| Job | Solution that demonstrates the gap | v1 (published) | v2 (kit) |
|---|---|---|---|

After all five rounds, `prove_all.py` in the kit gives 80 of 80 expected verdicts: every job against the untouched environment, every correct solution and every known wrong one, including these.

## Second round

The reviewer checked the fixes and found six more problems, all in the kit's v2 code, none in the published runs:

- **The classifier's last step still used the old reading.** "Use Redis-compatible Valkey" was coded Redis. Fixing it is what surfaced the answer corrected above; it is the only published answer whose code changes.
- **The cache grader rejected valid storage.** A product cached as base64 JSON, or in one field of a shared hash with its own expiry, failed. Both now pass, and both are in the proof set.
- **The search grader could still pass a search done outside the server.** It counted commands, so fetching every vector with a few large MGETs, or from one large value, passed. It now measures how much the server sends search.py per query (a search reply is a few KB; every vector is over 256 KB), and it removes the top article from the server and asks again, which also catches a copy of the vectors kept in a local file. It no longer forbids SCAN, which was never the problem.
- **The search grader was also too strict.** Two indexes of 500 articles failed, and an unrelated index of 1,000 passed. It now counts distinct article ids stored in the server.
- **The deadline baseline could be silently incomplete,** and a missing baseline disabled the check. Field expiry is now read according to what the server supports, other errors stop the run, and a missing baseline fails.
- **The proof driver could count a grader crash as an expected fail.** A check now counts only when the grader returns a valid verdict and the solution itself ran without error.

The proof set grew from 35 to 49 checks: new wrong solutions for each hole (bulk MGET, one large value, a local copy) and new correct solutions the graders must not reject (base64, field expiry, two indexes, SCAN to find an index). On real servers, the correct search solutions receive 2 to 5 KB per query; computing outside the server pulls 261 to 288 KB, whichever way the vectors are fetched; and the local copy, which reads almost nothing from the server, is caught by the removal check alone.

## Third round, 2026-10-07

The reviewer checked the second-round fixes: three were closed and three only in part. We fixed all six in the kit and said so here; the fourth round found two of those fixes incomplete (below). None of this is in the published runs, and no published number changes.

- **The removal check could be skipped, or survived by crashing.** It looked for the article's id only in key and field names, so when the id sat inside a record it skipped itself; and it failed only an answer that still returned the removed article, so a `search.py` that exited with an error passed. The article is now found by its id wherever its record holds it, the job fails if it cannot be found, and after the removal `search.py` must run cleanly and return the new top 5.
- **The byte limit was measured on a run that was not scored.** The search command was seen through MONITOR, whose own output the server counts as bytes sent, so the bytes were measured on a second run whose answers were not checked. The grader now reads the server's command counters instead, and one run per query is both measured and scored.
- **The count of articles accepted any id-shaped text**, including ids not in the article file, and missed ids stored in base64. It now counts only the 1,000 ids in the article file, unwrapping compression and base64.
- **The cache expiry took a hash field's TTL even when the whole hash expired sooner.** The sooner of the two now counts.
- **A broken grader was scored as the agent's failure.** It is now recorded as an error and left out of the score.
- **The proof driver did not check that each log belonged to its check.** It now checks the number of logs and that each one ran the planned job and solution.

The proof set grew from 49 to 61 checks. New wrong solutions, one per hole: a local copy of the vectors under opaque keys, a local copy that exits with an error once an article is missing, 900 articles plus 100 made-up ids, and an expiry of 300 s per field inside a hash that expires after 30 s. New correct solutions the stricter checks must not reject: opaque keys with the id only in a base64 field, and a shared hash kept for an hour with each field expiring after 300 s. On real servers, every correct search solution runs one search command per query (two with two indexes), receives 2 to 5 KB per query, and returns the right new top 5 once the article is removed; computing outside the server pulls 261 to 288 KB per query; the three local copies read about 1 KB per query and are caught by the removal check alone.

Re-checked on the published runs: all 30 search passes stored each article under its id, in a key name or a vector-set element name (from the code they left), so the removal check, now required, applies to every one of them. Running it needs the containers, which are gone.

What the graders still cannot see is now listed in the kit's README: a `search.py` that re-ranks a few hundred candidates from a server-side search itself, or that answers from a local copy and asks the server only which articles still exist; the 100 KB limit, which is a heuristic; articles stored without their id, which fail although their search may be correct; and a cached product split across several keys, where only the key holding its name has its expiry checked.

## Fourth round, 2026-10-07

The reviewer confirmed four of the six third-round fixes, found the other two incomplete, and found two new gaps, each with a solution that demonstrates it:

- **The count of articles still counted an id without its article** (third-round fix incomplete). A marker holding the id of one missing article (`SET marker:kb-1000`) counted as that article, and no held-out query ranks that article in its top 5. An article now counts only when its own embedding is stored with its id.
- **The removal check could break a correct record** (third-round fix incomplete). A record that names a related article holds two ids, so the check took it for a map shared by many articles, removed one field and left the article in the index; `search.py` then failed. The check now removes the record that holds the article's embedding, whatever other ids it mentions.
- **An update that wrote the product back without an expiry passed.** The cache's expiry was checked only before the price update. It is now checked after it too.
- **Six ids passed as five.** The grader read the first five lines. It now wants exactly five.

The reviewer also pointed out that a solution placed in `jobs/reference/` but not listed in `prove_all.py` proves nothing. `prove_all.py` now stops when it finds one.

The proof set grew from 61 to 72 checks: the reviewer's four cases (the related-article record as a correct solution, the other three as wrong ones), and two more correct solutions, in JSON documents and in a vector set, the formats two and three of the published search passes used, so the new count of articles is proven on them. On real servers, each wrong solution fails for its own reason: the marker leaves 999 articles stored with their embedding and kb-1000 only as an id, the update leaves product 7 with no expiry, and six ids fail the five-id rule.

Re-checked on the published runs, from the code they left: every published search pass stored each article's embedding with its id, in a format the grader reads (FLOAT32 or FLOAT64 bytes, JSON arrays, a vector set), and every published `search.py` asks the server for 5 results and prints one id for each.

## Fifth round, 2026-10-07

The reviewer confirmed the fourth-round fixes for the cases it had reported, found the removal fix still too narrow, and found three correct solutions the graders rejected and one plausible mistake they accepted. It worked from the code and with stubs, without containers; we reproduced every case on real servers.

- **A Lua script computing the similarity inside the server was rejected** (a correct solution). The prompt asks for the search to run inside the server, not for a particular command, and the grader counted only search commands. Server-side scripts (EVAL, FCALL) now count.
- **The removal check could delete 50 articles to remove one** (fourth-round fix too narrow). A hash of up to 50 fields was taken for one article's record, so a hash holding 50 articles was deleted whole. A hash now counts as one article's record only when it holds one article's embedding; a hash holding several is trimmed entry by entry.
- **A cache compressed with bzip2 was not recognised** (a correct solution). The grader now reads every compression in Python's standard library (zlib, gzip, bzip2, xz) as well as base64.
- **Product 12's expiry was never checked** (a plausible mistake: an expiry call left hard-coded to product 7). It is now.

Writing the Lua solutions showed one more: after the removal, a correct solution that walks its own set of article keys found the removed key there and failed. The removal now also takes the article out of lists and sets, as deleting it would.

The proof set grew from 72 to 80 checks: the four cases above, each on both products. On real servers each gives the expected verdict for its own reason; the product-12 case fails on product 12's expiry alone.

Re-checked on the published runs: no published search pass used a Lua script and no published cache used bzip2; a search pass that kept all its articles in one hash, beside its vector set, is read as a hash of several articles under both the old and the new rule.
