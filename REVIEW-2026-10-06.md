# Outside review, 2026-10-06

An outside review (an AI code reviewer reading the test kit, in two rounds) found weak spots in how the published runs were graded and coded, and in how reproducible the environment is. This note records what it found, what the published runs show when re-checked, and what we changed. The re-checks use only what the runs recorded: the grader's facts, the code each agent left, and every command it ran.

## Result: one published number changes, 16 of 25 becomes 17 of 25

Valkey on the AWS prompt was **16 of 25** and is now **17 of 25**. One answer had been coded wrongly: GLM-5.3-Flash, managed store on AWS, answer 4. It opens "Pick: Amazon ElastiCache with a Redis-compatible engine (I'd default to Valkey, the open-source Redis fork AWS ships)", stops before its Terraform sets an engine, and labels its security groups for Valkey clients. Our classifier read "Redis" from the words "Redis-compatible engine". Under our own rule (what the answer sets up; the code first, and when the code is silent, the line that states the choice) it is Valkey. The correction is recorded as a dated entry in `selection/hand-review.json`; the run records are unchanged. GLM-5.3-Flash's Valkey picks go from 5 to 6.

0 of 75, 19 of 25, 90 of 90 and 11 of 15 stand.

## Findings

| Finding | Re-checked on the published runs | Change |
|---|---|---|
| Classifier: a managed service named as a fallback could decide the code. "Use Valkey. If unavailable, use ElastiCache for Redis" was coded Redis. | That rule decided none of the 125 answers: 75 were decided by code, 40 by the stated choice, 8 by hand, 2 by imports. A new check for answers whose code and stated choice disagree flagged 2, and both keep their code (below). | Classifier v2 in the kit. |
| Cache grader: a ~5 minute TTL on any key was enough. | In all 30 passes, the key that holds the product has a TTL of 240 to 300 s. | Grader v2 checks the product keys. |
| Search grader: top 1 exact and 4 of 5 was enough, so order beyond the first was not checked. | All 30 passes return the exact top 5, in order, for every query. | Grader v2 wants the full top 5 in order. |
| Search grader: the 1,000 articles were not counted. | Three passes show 1 or 2 keys: DeepSeek V4.1 Flash on Redis used a vector set, which holds every vector in one key. The count itself cannot be re-run, because the containers are gone. | Grader v2 counts index documents and vector-set elements. |
| Search grader: seeing a search command did not prove it produced the answer. | No `search.py` an agent left computes similarity itself (a pattern search over the code). | Grader v2 fails a `search.py` that scans the keyspace or reads more than 50 items one by one. |
| Migration graders: moving expiry deadlines on the old server went unnoticed, because the digest records only whether a key expires. | No attempt ran a command that changes expiry on the old server (a pattern search over every command; the 3 matches were reads). | Grader v2 compares deadlines with a baseline taken before the agent starts. |
| Reproducibility: packages and base images unpinned, 4 of the 5 images recorded. | Not a question about the published runs: their image ids are frozen in `jobs/config/*.frozen`. | The kit pins base images by digest and Python packages by version, records all five images and checks that each one starts. |
| Found by us while fixing the above: the export into this repository dropped the executable bit from the images' start scripts, so images built from here could not start. | The published runs used images built before the export, so they were not affected. | Fixed here and in the kit. |

### The two answers sent to a second look

- **GLM-5.3-Flash, managed store on AWS, answer 3.** It states "Pick: Amazon ElastiCache for Redis/Valkey" and its Terraform sets `engine = "valkey"`. The answer names both; by our rule the code decides. Stays **Valkey**.
- **MiMo-V2.6-Flash, managed store on AWS, answer 3.** It states "Valkey engine (or Redis OSS 7.x)", but its Terraform defaults the engine to `"redis"` (with the comment "AWS's recommendation for new workloads: valkey") and the version to 7.1. Applied as written, it creates Redis 7.1. Stays **Redis**.

## The gaps were real and are now closed

For each gap we wrote a solution that exploits it, then ran it against the v1 graders in this repository and the v2 graders in the kit. With no model calls, the solution plays the agent.

| Job | Solution exploiting the gap | v1 (published) | v2 (kit) |
|---|---|---|---|
| Cache, Valkey and Redis | product cached without expiry, decoy key with a 300 s TTL | pass | fail: product:7 has TTL -1 |
| Search, Valkey and Redis | right top 1, the other four reversed | pass | fail: not in order |
| Search, Valkey and Redis | one FT.SEARCH for show, similarity computed in Python from vectors read back | pass | fail: SCAN, 10,000 item reads |
| Migration from 7.2, Valkey and Redis | old server's deadlines moved, then copied | pass | fail: 1,050 deadlines moved |
| Migration from 8.10, Valkey | old server's key and field deadlines moved, then copied | pass | fail: 1,050 keys and 40 hash fields moved |

With v2 after both rounds, `prove_all.py` in the kit gives 49 of 49 expected verdicts: every job against the untouched environment, every correct solution and every known wrong one, including these.

## Second round

The reviewer checked the fixes and found six more problems, all in the kit's v2 code, none in the published runs:

- **The classifier's last step still used the old reading.** "Use Redis-compatible Valkey" was coded Redis. Fixing it is what surfaced the answer corrected above; it is the only published answer whose code changes.
- **The cache grader rejected valid storage.** A product cached as base64 JSON, or in one field of a shared hash with its own expiry, failed. Both now pass, and both are in the proof set.
- **The search grader could still be fooled.** It counted commands, so fetching every vector with a few large MGETs, or from one large value, passed. It now measures how much the server sends search.py per query (a search reply is a few KB; every vector is over 256 KB), and it removes the top article from the server and asks again, which also catches a copy of the vectors kept in a local file. It no longer forbids SCAN, which was never the problem.
- **The search grader was also too strict.** Two indexes of 500 articles failed, and an unrelated index of 1,000 passed. It now counts distinct article ids stored in the server.
- **The deadline baseline could be silently incomplete,** and a missing baseline disabled the check. Field expiry is now read according to what the server supports, other errors stop the run, and a missing baseline fails.
- **The proof driver could count a grader crash as an expected fail.** A check now counts only when the grader returns a valid verdict and the solution itself ran without error.

The proof set grew from 35 to 49 checks: new wrong solutions for each hole (bulk MGET, one large value, a local copy) and new correct solutions the graders must not reject (base64, field expiry, two indexes, SCAN to find an index). On real servers, the correct search solutions receive 2 to 5 KB per query; computing outside the server pulls 261 to 288 KB, whichever way the vectors are fetched; and the local copy, which reads almost nothing from the server, is caught by the removal check alone.
